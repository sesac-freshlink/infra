# gateway 연결 풀이 알림 SSE로 다 차서 dev 알림 API가 모두 504

- 날짜: 2026-11-02
- 작성: 김진아
- 관련: gateway [#19](https://github.com/sesac-freshlink/gateway/pull/19) (머지 커밋 `a66db0a`)

## 증상

dev에서 `/api/notifications`, `/api/notifications/unread-count`, `/api/notifications/stream`이 모두 504였다. 김경우가 알려 줬다. 오전에는 SSE가 됐다.

gateway 로그:

```text
org.apache.hc.client5.http.ConnectionRequestTimeoutException: Timeout deadline: 180000 MILLISECONDS, actual: 180000 MILLISECONDS
```

notification-service 파드에 직접 요청하면 `unread-count`가 71ms에 200이었다. 서비스는 정상이었다.

## 환경·발생 조건

- 위치: gateway (Spring Cloud Gateway Server WebMVC 5.0.x, Spring Boot 4.0.8), dev 클러스터
- 어떤 작업 중이었나: 점주·고객 화면 여러 개가 알림 종(SSE)을 열어 둔 상태. 확인 시점에 알림 SSE 11개가 열려 있었다.

## 원인

- gateway는 서비스로 요청을 넘길 때 Apache HttpClient 5를 쓴다. 기본 연결 풀은 **서비스(주소) 하나에 5개**다.
- httpclient5는 우리가 넣은 의존성이 아니라 AWS SDK를 따라 런타임에 들어와 있었고, 풀 크기를 정한 적이 없었다.
- SSE(`/notifications/stream`)는 화면을 열어 둔 동안 연결 하나를 계속 잡는다(최대 30분).
- SSE가 5개 열리면 notification-service로 가는 연결이 다 찬다. 그 뒤 일반 요청은 빈 연결을 3분(기본 connection-request timeout 180초) 기다리다 실패하고, 그 전에 앞단(CloudFront·ALB)이 504를 돌려준다.
- 점주 매출 SSE(order-service `/owner/orders/sales/stream`)도 같은 위험이 있었다.

10/30 gateway #16 때 "SSE는 버퍼링·읽기 타임아웃만 보면 되고 따로 설정할 것이 없다"고 판단했는데, 연결 풀은 보지 않았다. 테스트도 SSE 하나만 열어 봤다.

## 해결

gateway에 `proxy/ProxyHttpClientConfig`를 더해 Boot의 `ClientHttpRequestFactoryBuilder`를 바꿨다.

```java
ClientHttpRequestFactoryBuilder.httpComponents()
        .withConnectionManagerCustomizer(pool -> pool.setMaxConnPerRoute(200).setMaxConnTotal(500))
        .withDefaultRequestConfigCustomizer(request -> request.setConnectionRequestTimeout(Timeout.ofSeconds(5)));
```

- 서비스당 200개, 전체 500개까지 연다. 풀이 모자라도 3분이 아니라 5초 안에 실패한다.
- `build.gradle`에 `org.apache.httpcomponents.client5:httpclient5`를 직접 의존성으로 넣었다(버전은 Boot가 관리).
- 머지 후 ArgoCD가 dev에 `gateway:a66db0a`를 배포했다.

```powershell
kubectl -n freshlink rollout status deploy/gateway
kubectl -n freshlink logs deploy/gateway | Select-String ConnectionRequestTimeout   # 0건
```

확인: 점주 계정으로 탭 6개 이상 열어 SSE를 여러 개 잡은 상태에서 `/api/notifications?page=0&size=20`이 42ms에 200, `unread-count`·`stream` 200(김진아). 김경우도 알림 동작을 확인했다.

급할 때 임시 조치: `kubectl -n freshlink rollout restart deploy/gateway`로 잡힌 연결을 풀 수 있지만, SSE가 다시 쌓이면 또 막힌다.

## 재발 방지

- 테스트 `GatewayApplicationTests.manyOpenStreams_doNotBlockOtherRequests`: SSE 8개를 연 채 `unread-count`가 3초 안에 200인지 본다. 설정을 빼면 6번째 SSE에서 실패한다.
- gateway `application.yml` SSE 주석과 README 3장에 연결 풀 이야기를 적었다.
- SSE를 새로 붙이면 "버퍼링, 읽기 타임아웃, 연결 풀" 세 가지를 같이 본다.
- 남은 일(선택): notification-service가 SSE 타임아웃 때 `text/event-stream` 응답에 JSON 오류를 쓰려다 `HttpMessageNotWritableException`(503 로그)이 난다. 원인은 아니지만 로그 잡음이라 `GlobalExceptionHandler`에서 SSE 요청은 건너뛰게 고친다.

## 참고 링크

- Spring Boot 문서: HTTP Clients → `ClientHttpRequestFactoryBuilder` 사용자 지정
- Apache HttpClient 5 `PoolingHttpClientConnectionManager` (기본 route당 5, 전체 25)
