# GitHub 예약이 늦거나 빠져 NAT 없이 노드가 떠서 dev 전체 503

- 날짜: 2026-10-20
- 작성: 김진아
- 관련: 이 문서를 더한 PR (`fix/I-01-nat-schedule`), 워크플로 `.github/workflows/dev-cluster.yml`, `modules/workflow-dispatch`

## 증상

화요일 아침 dev `/api`가 모두 503이었다. ALB 대상(gateway)이 0개였다. 김경우가 알려 줬다.

```text
PS> kubectl get nodes
No resources found
PS> aws eks describe-nodegroup ... --query "nodegroup.{status:status,scaling:scalingConfig}"
"status": "ACTIVE", "scaling": { "minSize": 0, "maxSize": 3, "desiredSize": 2 }
PS> kubectl -n freshlink get pods
gateway-7d998fbcbd-st247   0/1   Pending   0   14h
... (모든 파드 Pending)
```

노드 그룹 인스턴스 2대는 `running`(09:10 시작)인데 클러스터에 노드로 붙지 않았다.

## 환경·발생 조건

- 묶음/위치: `envs/dev/cluster` (NAT), `envs/dev/persistent` (`modules/scheduler` 노드 일정)
- 어떤 작업 중이었나: 평일 아침 자동 켜기. 사람이 손대지 않았다.

## 원인

두 가지가 겹쳤다.

1. **GitHub 예약(schedule)이 늦거나 빠졌다.** dev-cluster 워크플로의 예약 실행 기록:

   | 예약 | 원래 시각(한국) | 실제 시작(한국) | 한 일 |
   | --- | --- | --- | --- |
   | `10 12 * * 1-4` NAT 삭제 | 10/19 21:10 | 10/20 03:41 | NAT 3개 삭제 |
   | `0 14 * * *` NAT 정리 | 10/19 23:00 | 10/20 04:34 | 변경 없음 |
   | `0 0 * * 2-5` NAT 생성 | 10/20 09:00 | 돌지 않음 | 없음 |

   cron은 UTC로 맞게 적혀 있었다(한국 09:00 = UTC 00:00). 실행은 시작하자마자 정상으로 끝났으니 러너 문제가 아니라 GitHub가 실행을 늦게 만들거나 만들지 않은 것이다. GitHub 문서는 부하가 높으면 예약 실행이 늦거나 빠질 수 있고 매시 정각이 특히 붐빈다고 적는다. 2026-10-19 15:49–16:56 UTC에 Actions 장애도 있었지만, 21:10 예약은 그 전부터 늦었다. 같은 달 다른 저장소들도 정각을 피한 cron이 몇 시간씩 늦었다고 보고했다.

   **왜 빠졌는지는 GitHub 기록으로 확인할 수 없다.** GitHub는 예약이 실행되면 run을 만들고, 실행하지 않으면 run도 로그도 오류도 남기지 않는다. 그래서 웹 화면, `gh run list`, REST API 어디에서도 "왜 안 돌았는지"를 볼 수 없다(GitHub 토큰으로 로그인해도 같다). 대신 저장소 쪽 원인을 하나씩 지워서 GitHub 쪽 문제로 좁혔다.

   - cron 오타·시간대: `0 0 * * 2-5`가 main에 있고, 워크플로 안에서 `nat-on`으로 연결돼 있다.
   - 워크플로 비활성화: 아니다. 같은 파일의 다른 예약(21:10 NAT 삭제, 23:00 NAT 정리)이 같은 날 새벽에 늦게라도 돌았다.
   - 60일 무활동 자동 중지: 해당 없다. 저장소에 매일 커밋이 있다.

   남는 것은 GitHub가 예약 실행을 만들지 않은 경우뿐이다. 2026-08-26부터 "수동 실행은 되는데 예약 실행이 늦거나 아예 생성되지 않는다"는 보고가 이어지고 있다(참고 링크).

   처음 설계(aws-리소스-계획.md 6-5)는 "Actions 예약은 몇 분 늦을 수 있다"만 가정했고, 빠지는 경우를 감시하거나 다시 돌리는 장치가 없었다.

2. **노드 일정이 NAT를 확인하지 않는다.** EventBridge 노드 일정(화~금 09:10 desired 2)은 정시에 돌았다. 노드는 사설 서브넷이라 NAT 없이 뜨면 EKS API·ECR에 닿지 못해 부트스트랩에 실패하고, 그 인스턴스는 NAT가 생긴 뒤에도 다시 붙지 않는다.

## 해결

```powershell
# 1. NAT 켜기 (수동 버튼과 같다)
gh workflow run dev-cluster.yml --repo sesac-freshlink/infra -f action=nat-on

# 2. 붙지 못한 노드 인스턴스 지우기. 노드 그룹이 desired 2에 맞춰 새로 띄운다(3~5분)
aws ec2 describe-instances --region ap-northeast-2 --filters "Name=tag:eks:nodegroup-name,Values=freshlink-dev-nodes" "Name=instance-state-name,Values=running" --query "Reservations[].Instances[].InstanceId" --output text
aws ec2 terminate-instances --region ap-northeast-2 --instance-ids <위 ID들>
kubectl get nodes -w

# 3. 파드 다시 띄우기
kubectl -n freshlink rollout restart deploy
kubectl -n freshlink get pods -w
```

## 재발 방지

- 시각은 EventBridge Scheduler가 지킨다: `modules/workflow-dispatch`의 Lambda가 정해진 시각에 workflow_dispatch API로 dev-cluster를 실행한다(README 4-11). Terraform은 그대로 GitHub Actions에서 돈다.
- NAT 생성을 08:50으로 당겨 09:10 노드보다 20분 먼저 돈다.
- 워크플로 안의 GitHub 예약은 예비로 남기되 정각을 피했고, NAT 생성·클러스터 삭제는 한 번 더 돈다.
- 늦게 온 GitHub 예약은 한국 시각이 맞지 않으면 건너뛴다(늦은 NAT 삭제가 낮에 NAT를 지우지 않게).
